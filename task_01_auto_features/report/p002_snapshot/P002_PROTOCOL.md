# P002 — retrieval-only candidate generation

Статус: протокол фиксируется **до результатов P002**. Это development-эксперимент только о retrieval/candidate generation. В P002 нет обучения бустинга, пересчёта feature-моделей или итоговой test-оценки. После просмотра результатов параметры P002 не меняются; следующий вариант требует нового run ID и отдельной версии протокола.

## Данные и запросы

- Использовать ту же когорту из 64 uid и ровно те же сохранённые запросы P001: 1 349 train и 499 validation. Сверять query IDs, user IDs, timestamps, target IDs и split с P001 `queries.jsonl`. Для оценки метрик использовать только 499 validation-запросов; train-запросы нужны для baseline equality и causal replay.
- Зафиксированные границы в исходных timestamp units: начало train `9 752 280`, train end `20 125 775`, validation end/p85 `23 380 165`. Запросы P002 не создаются заново и не ресэмплируются.
- Фильтровать все event-строки с `timestamp >= 23 380 165` через PyArrow **до** `to_pydict`, перебора Python-строк, генерации кандидатов или расчёта любых статистик. Читать только `uid`, `item_id`, `timestamp`, `event_type` и нужные mapping-колонки. Если Parquet физически читает смешанную row group, это не означает, что test labels просматривались: в Python и в исследовательскую логику передаются только прошедшие Arrow-фильтр строки ниже границы. Не открывать, не считать и не сохранять показатели по целям p85 и позже.
- В каждом запросе использовать только историю с `timestamp < query_timestamp`; все события с той же меткой исключены из префикса. Офлайн-допущение о доступности logged event в момент его timestamp сохраняется. Artist/album используются как фиксированный снимок mapping P001.
- Каждый генератор получает только `user_id`, query timestamp и прошлую историю. `target_item`, `target_is_repeat`, `target_known_before` и сохранённый P001 `candidate_items` недоступны генератору: первые три содержат/раскрывают target-derived информацию, последний нужен только для последующей baseline equality проверки. Target и его pre-query strata-флаги передаются оценщику только после того, как candidate list сформирован и запечатан. Запрещено добавлять target задним числом, расширять пул по target или менять список после вычисления hit.

## Замороженные варианты

Во всех вариантах `K=100`, уникальные item ID, один и тот же query cohort, временной replay и доступный каталог — item, наблюдавшиеся у выбранных пользователей строго до query timestamp. Источник item ранжируется детерминированно; при равных источниковых score tie-break — `item_id ASC`. Quota-варианты обходят источники в порядке popular → repeat → artist → album, добавляя до указанной квоты ещё не выбранные item; оставшееся место до 100 заполняют ещё не добавленные item из popular pool. Недобор не заполняется будущими item.

| ID | Квоты popular/repeat/artist/album | Определение |
| --- | --- | --- |
| P002-Baseline | 25/25/35/15 | Воспроизвести P001 `CandidateGenerator` в точности: source lists ограничены первыми 100 item, artist/album profile берёт top 5 сущностей; сохранить точный порядок candidate IDs и сравнить с P001 на каждом из 1 848 train+validation queries. Это equality anchor. |
| P002-Repeat | 10/60/20/10 | Те же source rankings, глубины и top-5 artist/album profiles, что в P002-Baseline; меняются только заранее заданные квоты. |
| P002-Affinity32 | 10/20/50/20 | Для artist и album выбрать до top 32 профилей пользователя вместо top 5; вклад и ранжирование item внутри связного пула оставить как в P001 (`profile_count × log1p(past_global_listen_count)`), с deterministic item ID tie-break. Для quota выдачи использовать первые 100 item каждого source list. Расширенный affinity pool формируется только из item прошлого каталога. |
| P002-RRF | Top 100 из объединённого score | Для каждого из четырёх baseline source rankings собрать top 200 item: popular по прошлому listen count DESC; repeat по последнему прошлому listen DESC; artist/album по P001 related score с top 5 профилей. Объединить по `RRF(item) = Σ_s 1/(60 + rank_s(item))`, используя 1-based rank и только pools, содержащие item. Взять top 100 по RRF DESC, затем item ID ASC. Без квот и без добавления target. |

**Совместимость с exact baseline:** текущий P001 код фактически использует top 5 artist/album profiles и source lists до `max_candidates=100` (это подтверждено `src/run_pilot.py`). Поэтому P002-Baseline и P002-Repeat потребляют те же 100-позиционные source prefixes и тем самым могут точно совпасть с сохранёнными P001 candidates. При желании source rankings можно сохранить на глубине 200 для overlap-диагностики, но позиции 101–200 не входят в эти quota-кандидаты и не меняют их. Не подменять equality anchor глубиной 200: при дедупликации и overlaps это изменит хвост candidate list. Более широкие pools depth 200 полностью применяются для P002-RRF; top32 расширение profile применяется только к P002-Affinity32, чьи quota source lists также ограничены первыми 100 позициями.

## Оценка и аудит источников

- Основная метрика на validation — candidate recall, сначала по каждому запросу (1, если единственный target присутствует, иначе 0), затем среднее по запросам пользователя и среднее по пользователям. Дополнительно сообщить query-micro candidate recall и числители/знаменатели, число пользователей/запросов, долю retrieved targets и misses.
- Отдельно показать repeat/new и warm/cold по сохранённым до retrieval query-флагам (`target_is_repeat`, `target_known_before`): query/user denominators, target counts, candidate hits и candidate recall для каждого среза. Полный знаменатель — все 499 выбранных validation targets до отбора по warm/cold и до retrieval. Не исключать cold или пропущенные target-ы из общей метрики.
- Для каждого query/варианта сохранять исходные rankings/pools по источникам, множество их memberships/пересечений и финальные candidate IDs. Сообщать pairwise overlaps до квот; фактические внесённые уникальные кандидаты по квотным источникам после дедупликации; для RRF — членство в пулах и RRF contributions/ranks. Одну запись кандидата не считать несколькими уникальными добавлениями; отдельно показать all-source memberships и attribution.
- P002-Baseline обязан совпасть с P001 `candidate_items` **по точной последовательности ID** для каждого train и validation query. Любое несовпадение — fail/stop до метрик вариантов. Для четырёх вариантов запросы и target IDs общие, candidate IDs могут различаться по назначению; после формирования каждого списка target membership только читается для метрики.
- Не сравнивать retrieval-only candidate recall с NDCG P001 как эффект улучшения признаков: у них разные этапы/метрики. Не интерпретировать validation различия как итоговый test-эффект или качество полного промышленного каталога.

## Запуск и неизменность

До чтения данных runner должен записать run ID и SHA256 исходных P001 query file, трёх prepared inputs, config и кода. Завершённый output не перезаписывать и повторно in-place не запускать. При ошибке сохранить failed status и артефакты; любой повтор — новый run ID/каталог и причина. Лимиты: process RSS не выше 1 100 MiB, минимум 150 MiB доступной системной памяти, одновременно один тяжёлый процесс. При превышении остановиться, сохранить статус и не продолжать тот же запуск. Логировать длительность фильтрации/replay, построения pools и оценки, peak RSS, число query/candidates и размера artifacts.
