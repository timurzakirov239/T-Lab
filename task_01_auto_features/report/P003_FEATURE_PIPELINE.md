# P003 — точность оптимизированного расчёта признаков и ресурсы

Эксперимент продолжает P001/P002. Проверка точности завершена: все 17 001 600
значений совпадают побитно. В единственной свежей паре запусков новый вариант
оказался медленнее. Scale-256 остановлен при превышении заранее заданного
лимита RSS 1 100 МиБ; полной матрицы признаков для него нет.
Обучение и итоговый test не выполнялись.

## Что проверяли

До запуска закреплены [протокол](../configs/P003_PROTOCOL.md) и
[конфигурация](../configs/p003_features.json). Для профиля и сравнения взяты
ровно 1 848 запросов P001: 1 349 train и 499 validation, прежние кандидаты в
прежнем порядке, 64 пользователя. Окно и half-life равны 670 390 RAW единиц.
Используются 92 признака U/I/D/C/X. Имена и порядок колонок сохраняются.

История строго раньше запроса; события с его timestamp ещё не наблюдаются.
Цели и target-derived поля не передаются в feature engine. Исходный
`pilot_features.py` совпадает по SHA256 с замороженным P001. Полные результаты
P001 и P002 не менялись.

## Профиль и реализация

Один baseline replay с cProfile занял 224,826 с; полный runner — 232,289 с.
Из отдельных wall spans observe — 65,203 с, transform — 159,023 с,
материализация — 0,514 с. Это времена с накладными расходами профилировщика.
Их нельзя использовать как знаменатель ускорения.

В таблице cProfile `_Stats.count` вызван 7 813 696 раз; cumulative time
`_append_entity_features` — 68,169 с, `_append_counts` — 39,728 с,
`_append_decay_aggregate` — 24,968 с. Вложенные cumulative времена
пересекаются, поэтому их нельзя складывать. Значительная стоимость этих
вызовов обосновала проверку повторного использования промежуточных значений.

Отдельный `OptimizedFeatureEngine` наследует состояние и правила обновления
базового движка. Он вычисляет U-блок один раз на запрос, использует один
вызов count для all/short и хранит C/X значения общей сущности в кэше одного
transform. Кэш не переносится между пользователями, моментами и обновлениями.
Порядок суммирования и промежуточные Python float сохранены. Итоговая матрица
пишется по запросам в `.npy` memmap; полный массив не собирается в RAM.

Оба варианта запущены по одному разу в отдельных свежих процессах без cProfile.

Матрицы имеют dtype float32 и занимают по 68 006 400 байт значений
(64,856 МиБ; `.npy` дополнительно содержит 128 байт заголовка).
Проверены полное `numpy.array_equal`, побитные SHA256 значений и файлов,
порядок запросов/кандидатов, offsets/sizes и схема колонок. Все совпали.

- SHA256 значений: `3447df447e30d2663566ce97d0ba277c9be259246acf9188acce76c95adbab72`.
- SHA256 `.npy`: `42d34a7c92da2bcd77e8b7944a964c2afb938f6965bcf79b1a5c0fb832830308`.

Равенство дополнительно проверено независимым субагентом по memmap chunks.
Свежий baseline также полностью совпал с профилированной матрицей.

Новый replay в этой паре дольше в 2,23 раза. **Ускорения и экономии памяти
не получено.** Один парный замер не отделяет влияние реализации от изменения
условий исполнения; даже унаследованная observe-фаза заняла другое время.
Причина разницы не установлена. Повторных замеров с выбором лучшего результата
не проводили. Эти данные не подтверждают внедрение нового движка ради скорости.

## Ступень 256 пользователей

**Статус: failed, остановка по ресурсу.** Пик процесса — 1 101,16 МиБ при
лимите 1 100 МиБ. Минимум свободной системной памяти за запуск — 790,05 МиБ.
Полный runner до остановки занял 432,631 с. Это время незавершённого запуска.

| Этап | Измеренный результат |
| --- | --- |
| Подготовка данных | 37,384 с, завершена |
| Загрузка development и выбор запросов | 15,457 с, завершены |
| Генерация кандидатов | 330,140 с, завершена |
| Запросы | 7 728: 5 625 train и 2 103 validation |
| Кандидаты | 772 800 строк, ровно 100 на запрос |
| Признаки до остановки | 1 441 завершённый запрос, 144 100 записанных строк |
| История в последнем checkpoint признаков | 476 179 наблюдённых событий |

История обновлялась дальше последнего завершённого запроса; checkpoint
`events_observed` относится к нему. Ошибка возникла при следующем наблюдении
истории. Файл memmap заранее имеет полный размер под 772 800 × 92, но его
незаписанный остаток не является рассчитанными признаками. Его запрещено
использовать как завершённую обучающую матрицу. Статус, partial output,
закреплённые запросы и подготовленные данные сохранены отдельно.

До расчёта признаков отдельно подготовлена случайная когорта из 256 UID
с seed 20261025: 1 216 363 опубликованных события полной истории и
1 042 027 development-событий. У 248 выбранных UID есть события до cutoff;
пересечение с исходной когортой — 64 UID. Подготовка заняла 37,384 с.
Повторная выборка запросов меняет query set; это не сравнение качества
рекомендаций между когортами. Не установлена полнота относительно Yambda-5B.

Cutoff `23 380 165` и остальные границы P001 не пересчитывались. Arrow
отфильтровывает поздние строки до Python-обработки. Полная история отдельно
сохраняется без интерпретации post-cutoff payload. Кандидаты — фиксированный
P002 repeat-heavy K=100; цель в список не добавляется. Входы признаков
фиксируются отдельно от labels. RSS ограничен 1 100 МиБ, резерв свободной
системной памяти — 150 МиБ. Частичный запуск сохраняется как failed и не
перезапускается поверх своего каталога.

Для 256 пользователей этот вариант не уложился в выбранный локальный бюджет.
Полный peak RSS не измерен, поэтому из остановки нельзя вывести точный размер
памяти успешного запуска. VPS с 16 ГБ RAM может дать запас для следующего
scale-эксперимента; это ориентир, а не измеренный минимум. Исследование
автоматических признаков можно продолжить локально на проверенной когорте64.
Перед увеличением расходов полезно отделить стоимость источников кандидатов,
состояния истории и resident страниц memmap отдельным будущим замером.

## Воспроизведение

Прошли 56 синтетических тестов. Verifier P003 проверил 21 файл компактных
доказательств, 28 локальных output hashes и повторно сравнил все 17 001 600
ячеек. Отдельная копия только compact evidence и verifier, без датасетов и
матриц, прошла проверку 21 файла; численный replay в этой копии не выполнялся.
Контрольные точки P001 и P002 также повторно прошли свои проверки.

Из корня проекта, в подготовленном Python-окружении:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s task_01_auto_features/tests -q
.\.venv\Scripts\python.exe task_01_auto_features/src/verify_feature_checkpoint.py
```

Для новых запусков используйте новые каталоги `--output`; завершённые или
частичные каталоги не перезаписываются. Профиль, затем baseline и optimized:

```powershell
.\.venv\Scripts\python.exe task_01_auto_features/src/run_feature_benchmark.py --engine baseline --profile --output task_01_auto_features/artifacts/p003_profile_REPRO
.\.venv\Scripts\python.exe task_01_auto_features/src/run_feature_benchmark.py --engine baseline --output task_01_auto_features/artifacts/p003_baseline_REPRO
.\.venv\Scripts\python.exe task_01_auto_features/src/run_feature_benchmark.py --engine optimized --output task_01_auto_features/artifacts/p003_optimized_REPRO
```

`verify_builds` из `src/run_feature_benchmark.py` сравнивает сохранённые
сборки и создаёт новый gate. Scale runner принимает его через `--gate`,
перепроверяет provenance и пишет новый каталог `--output`.

P003 проверяет вычисления, а не способность автоматически находить полезные
признаки. Следующий исследовательский этап должен сравнить ручной набор,
автоматическое построение/отбор и их объединение на одинаковых кандидатах.
P001, P002 и отрицательный результат по скорости P003 включаются в итоговый отчёт.
