## Простые оптимизации с сохранением значений

1. **Посчитать user-only блок один раз на запрос.** Сейчас `_append_counts(row, user_stats, timestamp)` вызывается для каждого кандидата, хотя U одинаков для всех кандидатов одного `(user_id, timestamp)`. Извлечь те же десять значений до item-loop, затем добавлять их к каждой строке без повторных `_Stats.count`, `total`, `recent/bisect` и `recency`. При 184 800 candidate rows существующая структура вызывает до 8 `_Stats.count` на U-append, то есть до 1 478 400 вызовов для U-блока; это подсчёт из цикла, не замер времени. Проверить равенство каждой float32-колонки.

2. **Одно чтение all/short на сигнал вместо двух.** В `_append_counts` внешний цикл по `all` и `short` дважды запрашивает `stats.count(signal, ...)`, хотя каждый вызов уже возвращает оба счётчика. Аналогичная структура есть в `_append_entity_features`: два окна повторно читают одни и те же entity-series. Перестроить расчёт по `signal`: один вызов `count` возвращает `(all, short)`, оба значения добавить в исходном порядке. Это сокращает обращения к Stats/series и `bisect` примерно вдвое для этих блоков, сохраняя границу окна и префиксные суммы. Не округлять промежуточные значения иначе.

3. **Query-local cache user-entity для C/X.** В одном `transform` один artist/album может встретиться у нескольких кандидатов; сейчас для каждой пары candidate-category заново ищутся `(user_id, entity_id)` и вычисляются counts/short-window/decay. Сначала собрать уникальные категории кандидатов запроса, посчитать по каждой категории нужные per-signal значения ровно один раз, затем агрегировать их в max/mean/knownshare для каждой строки. Кэш должен быть локален одному `(user_id, timestamp)` вызову, не менять состояние engine, дедуплицировать только уникальные entity ID mapping и сохранять mean по числу уникальных категорий. Это не плотная user-item матрица: размер временного кэша пропорционален числу различных artist/album в кандидате-пуле запроса.

**Не считать оптимизацией без профиля:** artist/album mapping уже normalise/deduplicate/sort один раз в `FeatureEngine.__init__`; `transform` повторно не перестраивает эти tuples. Его `.get` и обход entity повторяются на каждого кандидата, а не normalization.

**Проверка предложений:** сначала отдельно подтвердить user-level reuse и all/short count reuse (пункты 1+2); C/X query-cache реализовать только если профиль покажет повторы entity как значимую долю; отдельно оценить выходную матрицу. Все изменения держать в новой экспериментальной копии с exact-value differential check, не в замороженном P001.

## Короткий микропрофиль

Проводить только после закрытия независимой проверки P002; P001 source hash и его артефакты не переписывать. Одна отдельная development-копия результата, без обучения:

1. Зафиксировать неизменные cohort metadata, полный сохранённый query ID/order, causal event prefix, mappings, `short_window_raw=201117` и `half_life_raw=670390`. Это значения одного имеющегося build, выбранные только для воспроизводимой точки измерения, а не по качеству модели. Сверить входные хеши с P001.
2. Один исходный replay пройти под `cProfile` и отдельными wall-clock spans на replay/`observe`, `CandidateGenerator.candidates`, `FeatureEngine.transform`, `np.asarray`/формирование query matrix и итоговую `np.concatenate`. Зафиксировать количество вызовов, cumulative time, peak RSS и final matrix bytes. Профилирование не включает CatBoost.
3. Проверить исходные значения на повторном запуске без profiler (один раз) на тех же query IDs. Профилировщик влияет на wall time, поэтому его время — локализация затрат, не сравнение скорости.
4. В отдельной экспериментальной копии применить последовательно оптимизацию 1+2; повторить тот же вход и сравнить массивы candidate rows по shape, dtype и точному float32 values или SHA256 сохранённых matrix bytes. Повторить отдельный, не профилируемый time/RSS build. Если профиль показывает доминирование array/list conversion или лишний peak RSS, отдельным последующим экспериментом проверить заранее выделенный transform output buffer; не включать это без такого сигнала.
5. Критерий: все матрицы имеют ту же форму и значения, query/candidate ID упорядочены идентично, причинные проверки не меняются; замеряется wall time подготовки и peak RSS. Сохранить оба набора цифр, не выбирать новые параметры/модель и не запускать обучение.

## Проверка масштаба 256 пользователей

Не экстраполировать 64-user runtime как результат. Для предварительной оценки использовать только линейную оценку: 4× измеренная нагрузка P001 означала бы около 739 200 candidate rows и примерно 259.4 MiB финальной матрицы; это расчёт из 184 800 × 4 и 64.856 × 4, не замер. Истории неоднородны (max 27 240 строк против median 2 046), поэтому случайная когорта из 256 пользователей может заметно отличаться.

Короткая фактическая проверка после согласования отдельного запуска: построить 256-user development cohort без обрезания histories; взять тот же протокол query selection и тот же фиксированный validation/train ID порядок для общей 64-user части, затем добавить оставшихся 192 пользователя согласно заранее зафиксированному sampling seed. Сначала посчитать metadata и суммарные event/query/candidate counts; feature build запускать только если пределы ресурсов позволяют. Для одной feature конфигурации измерить peak RSS и время, без обучения. Не включать test и не менять P001.

## Следующее действие

Сначала получить микропрофиль; затем сделать только value-preserving оптимизации 1+2, если повторные вызовы занимают заметное время; C-cache — только при измеренной доле повторных entity, а output buffer — только при подтверждённой стоимости материализации. Запросить отдельное подтверждение независимого рецензента на profile результатов; до него не менять P001 код и хешированные outputs. Масштаб 256 оценивать после проверки exact-value equivalence и ресурсов, а не по предполагаемому ускорению.
