# Yambda-50M: локальный аудит данных

Дата: 2026-10-25. Проверялись локальные файлы версии из [download_manifest.json](../data/download_manifest.json); их хеши и размеры ранее были сверены при загрузке. Детальные полные проходы запускались, затем были прерваны без сохранённого результата. Завершена только инвентаризация Parquet metadata; артефакт: [metadata_audit.json](../artifacts/data_audit/metadata_audit.json), `full_scan_completed=false`. Скрипт [inspect_yambda.py](../src/inspect_yambda.py) по умолчанию выполняет metadata-only; режим полного прохода экспериментальный.

## Проверено на локальных файлах

Parquet metadata/schema прочитаны через PyArrow 26.0.0. `multi_event.parquet` содержит **47,790,449 строк** в 183 row groups (название 50M не означает ровно 50 млн). `artist_item_mapping.parquet` содержит 9,271,906 строк; `album_item_mapping.parquet` — 9,651,644 строк. Схемы колонок и физические типы сохранены в JSON артефакте. Локальные метаданные не подтверждают фактические значения ячеек.

Документация источника утверждает сортировку событий по `(uid, timestamp)` и время в пятисекундных bins. Она не объясняет epoch anchor для абсолютной интерпретации времени. `played_ratio_pct > 100` допускает перемотку и повторное прослушивание, поэтому такие значения не следует автоматически считать ошибками. Параметры 50M, 500M, 5B в README являются масштабами публикации. Локальные проверки хеша/metadata **не доказывают**, что 50M — случайный/репрезентативный срез, что это полные истории выбранных пользователей или что они сохраняют временную полноту относительно 5B.

## Ресурсы и границы вычислений

На машине: Python 3.12.10; локально создан `.venv`, PyArrow 26.0.0; NumPy 2.5.4 используется полным режимом скрипта и установлен локально, его версия также записывается в metadata-отчёт. Глобальный Python не менялся. CPU: Intel Core i5-10210U, 4 ядра / 8 потоков; GPU: интегрированная Intel UHD. RAM: 8 GiB; наблюдавшийся свободный объём менялся примерно от 0.7 до 1.0 GiB. Полные проходы прерваны до завершения; принят только metadata-режим. Модели не обучались.

Не посчитаны: уникальные пользователи/объекты по строковому проходу, event counts, timestamp range/ties, история на пользователя, user-item повторы, null/range `played_ratio_pct`, coverage mappings и фактическая сортировка. Точный повтор user-item можно считать по одному пользователю с set и очищать его на границе пользователя только после подтверждения сортировки. Полный режим скрипта не является принятой реализацией: требуется проверить обработку одинаковых timestamp на границах batch (в частности, межbatch-счётчик строк и групп), а также фактическую сортировку. До этой проверки нельзя использовать его результаты для выводов.

## Рабочая рекомендация

Для пилота предлагаю оставить весь опубликованный 50M-файл (фактически 47.79 млн событий) как единицу данных и не обрезать пользовательские истории; ограничивать пилот лучше числом обучающих примеров/кандидатов после постановки и разбиения. Это предложение, не принятое решение и не утверждение полноты относительно 5B. Требования к памяти зависят от реализации и масштаба; для дальнейшей работы нужна потоковая или дисковая обработка и замеры на выбранном пайплайне.

## Воспроизведение

Из корня репозитория metadata-only выполняется по умолчанию (флаг `--metadata-only` сохранён для совместимости):

```powershell
.\.venv\Scripts\python.exe task_01_auto_features\src\inspect_yambda.py --metadata-only
```

Фактический результат: `task_01_auto_features/artifacts/data_audit/metadata_audit.json`. В JSON записаны дата выполнения, версии Python/PyArrow/NumPy, схемы, row counts и row groups для трёх файлов, а также `full_scan_completed=false`. NumPy используется полным режимом. Полный экспериментальный скан не запускайте для выводов до проверки обработки batch boundaries; технически он требует явных флагов `--full-scan --allow-experimental`. Скрипт не изменяет исходные Parquet. Все свойства, требующие чтения строк, остаются непроверенными.
