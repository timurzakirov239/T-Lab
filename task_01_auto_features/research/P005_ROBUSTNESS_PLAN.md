# P005 — проект проверки устойчивости после P004

Статус: исторический проект; P005 завершён по отдельному [замороженному протоколу](../configs/P005_PROTOCOL.md). [Результаты и ограничения](../report/P005_ROBUSTNESS.md). Ниже сохранена исходная постановка.
P004 реализовал ограниченный DSL/отбор и показал небольшие development-различия:
A1 NDCG20 выше Manual UIDC при худшем Recall; A2 не лучше A1 по NDCG;
Union совпадает с Manual. Одна когорта и один seed не подтверждают устойчивость.

Предлагается следующая локальная ступень с отдельным протоколом до результатов:

1. Две новые development-когорты по64 UID с полными опубликованными историями,
   независимые seed20261026/20261027. До выбора фиксировать правило взаимного
   исключения UID, чтобы новые когорты не пересекались с P004 и друг с другом.
   Не подбирать пользователей по активности или качеству. Сохранить исходную
   population/membership и ограничения офлайн-когорты.
2. Оставить RAW границы P001, грамматику206 и те же candidate quotas/K100.
   Arrow фильтрует p85+ до Python; истории до cutoff не обрезать. Запросы
   формировать по прежним правилам до30train/10validation на пользователя.
   Ни p85+ target, ни его event payload не исследовать.
3. Повторить полностью закреплённый алгоритм P004 inner selection на каждой
   новой когорте, включая pruning и предложения. Не переносить только удачный
   поднабор P004 как будто он был заранее известен. Дополнительный вариант
   переноса фиксированного поднабора возможен лишь как отдельное заранее
   названное сравнение. Model budget/seed и masks задаются до результатов.
4. Основные фиксированные controls: Manual UIDC и Manual I. Отдельно AutoA1,
   AutoA2 и Union, выбираемый по inner score. Для оценки устойчивости считать
   per-user paired deltas и направление эффекта на каждой когорте; при таком
   размере не заявлять популяционную значимость. Показать и отрицательные результаты.
5. Сопоставить выбранные выражения и группы между когортами: частота выбора
   окон/операций, размер набора, влияние новых A2 выражений. Частое включение
   в модель не считать доказательством причинного вклада. Для attribution
   нужны заранее фиксированные ablations, не подбор на внешних результатах.

Исполнять когорты последовательно отдельными процессами с RSS1100МиБ и
резервом150МиБ, сохранением failed subrun и новым ID при исправлениях.
P004 peak678,77МиБ обосновывает попытку64 локально, но не гарантирует
успех на другой истории. При превышении не урезать отдельные истории и
не повышать бюджет задним числом. Масштаб256 в P003 остаётся failed.

Перед запуском доработать P004 runner: его hash guard намеренно запрещает
смену конфигурации. Нужен отдельный runner/config/protocol P005 и проверенная
подготовка новых данных; P004 и его source hashes сохранить. Не снимать
гейт простым ослаблением проверки.

Только после проверки устойчивости и фиксации итогового метода планировать
однократную финальную test-оценку по отдельному заранее записанному протоколу.
Исследование источников новых кандидатов остаётся отдельной задачей: эффект
retrieval нельзя смешивать с эффектом признаков. Работа2 по-прежнему отложена.
