# P004 — ограниченный поиск автоматически построенных признаков

Обновление после реализации: P004 завершён по уточнённому
[протоколу до запуска](../configs/P004_PROTOCOL.md), [результаты](../report/P004_AUTO_FEATURES.md).
Ниже сохранён исходный проект плана. Окончательные DSL206,9inner+11finalfits,
критерии и гейты определены протоколом; P003 failed scale256 не является
препятствием для принятого exact64. Следующий этап — [проект P005](P005_ROBUSTNESS_PLAN.md).

**Статус: план; не реализован и не запущен.** Цель — проверить на сохранённой 64-пользовательской P003-выборке, можно ли программно породить и отобрать признаки для ранжирования, сравнить их с ручным `FeatureEngine` и их объединением. Это proof-of-method на малой когорте, не доказательство качества или масштабируемости. Работу на 256 пользователях планировать только после измеренных времени и памяти P003.

## Протокол и входы

Вход — замороженные P003 development артефакты: 64 полные доступные истории, уже сформированные query/candidate ID, метки train/validation и ручная feature matrix, необходимые для точного join по `(query_id, item_id)`. Повторно не выбирать пользователей, запросы или кандидатов; исходные `events_full.parquet` и исходные 50M в P004 не сканировать. Если P003 не сохранил воспроизводимые query/candidate IDs и историю до запроса, P004 остановить до их подготовки отдельным проверяемым этапом.

Применяется [PILOT_PROTOCOL.md](../configs/PILOT_PROTOCOL.md): raw timestamp, границы p30/p70/p85, equal timestamp не разрываются, перед query доступны лишь события с `timestamp < query_time`; target и события той же временной метки исключены. Календарную интерпретацию времени не вводить. В пилотном сравнении p85+ остаётся недоступен: не сканировать, не генерировать признаки и не считать статистики зарезервированного периода. Время доступности mappings не доказано; они остаются явно принятым фиксированным snapshot допущением, одинаковым для всех вариантов.

Качество и candidates оцениваются только на идентичном замороженном наборе запросов/candidates. Использовать существующие лимиты пилота: до 30 train и 10 validation queries на пользователя, K=100, CatBoost 120 итераций, depth 5, learning rate 0.07, 2 CPU потока, фиксированный seed; target отсутствующий в candidate pool остаётся пропуском в end-to-end знаменателе. Обучение условно только на query, где target найден, как оговорено в протоколе. Другие настройки модели или candidates в этом этапе не подбирать.

**Внутренний временной отбор:** разбить train queries только хронологически. Граница — p70 распределения train query timestamps: ранние query идут в inner fit, более поздние в inner selection; равные timestamps не разрываются, фактические counts сохраняются в manifest. Порог считается по запросам, не по всем событиям. Отбор признаков использует только этот внутренний selection fold; правила DSL фиксируются заранее. После фиксации выбранного набора ручной baseline, automatic set и union переобучить на всём допустимом train p30–p70, затем один раз сравнить на p70–p85. Inner split уменьшает прямое использование внешней validation для отбора, но P001 уже многократно использовал development validation; поэтому P004 — исследовательское сравнение с повторным dev exposure, не независимое подтверждение. После просмотра p70–p85 наборы/окна/DSL не править по результату. Итоговый test не открывать.

## Автоматическая генерация и отбор

«Автоматический» здесь означает детерминированное построение выражений из заранее объявленного DSL и программный выбор под фиксированным бюджетом. Ручное проектирование самого DSL остаётся человеческим вкладом; не называть его автономным открытием признаков. Текущие вручную заданные признаки `FeatureEngine`, включая U/I/D/C и X/half-life, относятся только к ручному control, не засчитываются как автоматически найденные.

Генератор строит таблицу specs с `feature_id`, `group`, источником, формулой/операторами, event type, окном и provenance; затем materializer вычисляет только выражения, допустимые для конкретного query prefix. Максимум **256 кандидатных колонок** до отбора. Пространство ограничить:

- **Сущности:** пользователь U, item I, точная пара user–item D, user–artist/album C. Mapping entity ID уникализировать; для C вклад одного события делить на число уникальных entity связей.
- **События:** зарегистрированные `listen`, `like`, `dislike`, `unlike`, `undislike`; не трактовать пропуск события как отрицательную реакцию. Не использовать `played_ratio_pct`, `track_length_seconds`, `is_organic` как признаки без подтверждения времени доступности.
- **Агрегаты:** causal count/sum, unique item/entity count, last-event recency/known, event share с явно заданным знаменателем и сглаживанием, short-vs-previous-window trend. Не генерировать CTR/conversion: в данных нет логов показов/экспозиции.
- **Окна:** вся история до query и P001 raw-временные доли `1/100`, `1/30`, `1/10` от development span `(p70 - min timestamp)`. Перевода в дни/секунды нет. Trend использует два непересекающихся окна одинаковой длины строго до query; формулу фиксировать в spec до запуска.

Генератор отбрасывает недопустимые/дорогие выражения, затем константные признаки и дубликаты по точным значениям на внутреннем fit-fold; schema, порядок, причины отбраковки и хеш спеки сохраняются. Нельзя использовать метрики внешней validation для генерации/отсева. Внутренний отбор — максимум **16 CatBoost оценок** serially: до 8 в одинаковом с ручным семействе (A1) и до 8 в расширенном пространстве окон/агрегатов (A2). В каждой оценке те же train queries, candidates, модельный бюджет и inner selection split; выбор по inner user-macro NDCG@20, равенства — меньше колонок, затем стабильный `feature_id`. Любая попытка считается в лимите, включая упавшие/неудачные. A1 отделяет пользу поиска от расширения пространства; A2 проверяет ограниченные дополнительные выражения.

## Сравнения и абляции

Отчёт разделяет три набора, все признаки joined к тем же `(query_id, candidate_id)` и рассчитаны из того же causal prefix:

1. **Manual:** текущий ручной набор U/I/D/C из P001 `FeatureEngine` (ручной X фиксировать отдельно, не смешивать с automatic).
2. **Auto:** только признаки, выбранные алгоритмом из A1/A2; указать их DSL provenance и число кандидатов/удалённых колонок.
3. **Union:** manual + выбранный automatic set с удалением точных дубликатов; одинаковые выражения не считать новым вкладом.

Для ручного пути проверить U/I/D/C вклад по существующей схеме EXECUTION_PLAN: I, U+I, U+I+D, U+I+C, U+I+D+C, полный набор без каждой группы с переиспользованием совпадающих конфигураций; отдельно C-artist и C-album. Группы automatic и union маркируются U/I/D/C теми же правилами, затем для лучшего frozen union сделать leave-one-group-out, не выполняя новый отбор на внешней validation. Всего ограничить этап **28 CatBoost fit**: до 16 inner search, до 10 уникальных ручных ablation/control fit, плюс финальные Auto и Union; повтор полного Manual использовать среди этих десяти, не дублировать без причины. Если дублирование или нехватка данных уменьшает число запусков — сократить, не добирать попытки вне бюджета.

Основные метрики — user-macro NDCG@20 и Recall@20, candidate recall/coverage и доля target в кандидатах; query-micro только дополнительная. Сохранить также разности Auto–Manual и Union–Manual по каждому пользователю/запросу. При 64 пользователях интервалы и малые сегменты нестабильны: показывать знаменатели, не объявлять статистически надёжное превосходство.

## Гейты и ресурсы

1. **Перед генерацией:** Stage3 должен иметь принятый exact-value optimization и сохранённую 64-матрицу/query/candidate manifest. На tiny fixtures проверить, что изменение любых событий с `timestamp >= query_time` не меняет ни одно прошлое выражение; target и равный timestamp исключены; повторный mapping link не размножает счётчик; каждое выражение повторно воспроизводимо.
2. **64 users:** сначала только method proof и профиль стоимости. Один процесс, 2 CPU потока; monitor из Stage3, пределы памяти/резерв — актуальные значения Stage3 и конфигурации запуска. Ограничить 256 колонок, 16 inner fits, 28 суммарных fits. Сохранить время генерации, материализации, отбора, обучения, оценки, peak RSS и число query/candidate/features.
3. **До 256 users:** переход разрешён, только если Stage3 показал достаточный фактический RSS запас для матрицы признаков, бустинга и копий, а 64-run проходит лимиты без прерывания. Увеличение пользователей не менять одновременно с числом candidates/features или модельным бюджетом. Если лимиты нарушены — завершить на 64, сохранить failed status и сузить DSL/число inner fits; не обрезать историю.

Сохранить конфиг, DSL/spec hash, кодовый hash, split/query/candidate IDs, feature provenance, все inner scores, попытки включая ошибки, frozen наборы и prediction/metrics artifacts. Результат P004 — воспроизводимость, найденные/не найденные допустимые expressions, качество и стоимость в рамках этой сетки. Не обещать превосходство; последующее расширение потребует отдельного зафиксированного бюджета и нового development-дизайна.
