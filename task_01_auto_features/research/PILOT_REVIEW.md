# Пилотная оценка: реализация метрик

Область: независимая функция ранжирования для пилотных запросов. Это проверка логики метрик на синтетических данных, не измерение качества рекомендаций. Реальные test-метрики не рассчитаны; последние 15% временной шкалы остаются зарезервированным test-периодом.

## Контракт реализации

`src/pilot_evaluation.py` реализует `evaluate_ranking(queries, scores_by_query, ks=(10, 20))`. Функция использует ровно переданные candidate lists и не вставляет target. При сортировке оценки идут по убыванию, равные оценки разрешаются по возрастанию item ID. Target, отсутствующий среди кандидатов, получает ноль для Recall/NDCG и остаётся в знаменателе. `candidate_recall` сообщает долю target-ов, присутствующих среди кандидатов; он не заменяет end-to-end retrieval генератора.

Вывод включает общие метрики, разбиение train/validation, срезы repeat/new и warm/cold (`target_known_before`), количества и покрытие. Для каждого среза возвращаются query-micro и user-macro метрики. User-macro сначала усредняет запросы каждого пользователя и затем пользователей, поэтому частые пользователи не получают лишний вес. Оценщик отклоняет длины score, несовместимые с числом кандидатов, недопустимые NaN/inf и повторяющиеся candidate IDs. Он не проверяет временные границы, полноту истории или причинность признаков: это ответственность протокола/runner-а.

Для согласованности с пилотным контрактом ожидается, что запросы уже сформированы из полных историй выбранных 64 пользователей; split и target подготовлены runner-ом согласно train_end=p70, validation_end=p85, query_start=p30, а признаки используют только RAW timestamps и события, доступные строго раньше query timestamp. Целевая метка — ровно следующий logged listen. Эти условия не выводятся из метрик и здесь независимо на данных не проверялись. Test split намеренно отсутствует в разрешённых значениях evaluator.

## Проверки

Синтетические unit tests покрывают пропущенный target и сохранение знаменателя, детерминированную ничью независимо от порядка входных кандидатов, отличие user-macro от query-micro, аналитическое значение NDCG при ранге 3, `K` больше числа кандидатов, дубли candidate ID, NaN и несовпадение числа score с кандидатами.

Проверки не используют локальные реальные данные, не рассчитывают метрики моделей и не открывают зарезервированные test labels. Полный набор тестов проекта в среде без `pyarrow` может не импортироваться; тесты этой функции можно запустить отдельно стандартным `unittest` из `task_01_auto_features`.

## Независимое ревью runner-а

Файлы проверены без запуска дорогого пилота: `src/run_pilot.py`, `src/pilot_features.py`, `configs/PILOT_PROTOCOL.md`, `configs/pilot_001.json`. Принятые ограничения — квантильные границы и окна в исходных RAW timestamp units, фиксированный снимок artist/album mapping и предположение офлайн-replay о доступности события по logged timestamp. Это не подтверждает реальное время поступления записи.

**Блокирующих ошибок по проверенным требованиям не обнаружено.** Код выбирает train/validation запросы относительно глобальных границ p30/p70/p85; одинаковый `uid,timestamp` с несколькими listen исключается; интервалы не пересекаются и запросы из зарезервированного `t >= p85` не создаются. В replay агрегаты и генератор получают только строки `timestamp < query_time`. Генератор собирает кандидатов из уже наблюдавшегося каталога и не получает target как вход, поэтому target не может быть вставлен задним числом. Тестовые окна используют один и тот же список query/candidates с явной проверкой. Метрики получают все выбранные validation-запросы, включая target misses, а train-фильтр использует лишь запросы с retrieved positive. Матрица отбирается по именам групп U/I/D/C/X; item ID используется как tie-break по возрастанию. Runner не вызывает оценку test: запрашиваются только интервалы ниже p85, включена защита от `test_evaluation=true`, а результат помечен `final_test_evaluated=false`.

Сохранение включает run status/metrics JSON, хеш конфигурации и исходного кода, запросы, модели, предсказания и хронометраж; есть мониторинг RSS и системной свободной памяти с остановками на контрольных точках. Реальный resource profile этим review не измерялся.

Два ограничения для дальнейшей интерпретации и воспроизводимости:

- Warm/cold и retrieval знаменатель в метриках — все **выбранные** validation-запросы после лимита 10 на пользователя, не все подходящие validation-запросы. Runner сохраняет число подходящих до семплирования по split, но не считает их warm/cold/retrieval-срезы. Отчёт должен назвать метрики оценкой выбранного query-sample и показывать доступные количества до/после семплирования.
- Первоначальное замечание: runner не сохранял хеши трёх подготовленных Parquet. **Исправлено до завершённого запуска:** `prepared_data_sha256` в `run_status.json` содержит SHA256 `events.parquet`, `artist_mapping.parquet`, `album_mapping.parquet`; последующая независимая проверка подтвердила совпадение. См. [проверку результатов](PILOT_RESULT_REVIEW.md).

Добавлены четыре синтетических runner-теста: глобальные временные границы и исключение равновременной неоднозначности; детерминированный candidate tie-break и catalog-only выдача; replay строго до `t` без включения target timestamp; train только на retrieved positives при полном знаменателе выбранной validation-выборки. Команда интеграционной проверки в корне `D:\bot\T-Lab`:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s task_01_auto_features/tests -p 'test_pilot*.py' -v
```

Фактический результат: 23 теста прошли (`OK`). Ни обучение на реальных данных, ни итоговая test-оценка в рамках ревью не выполнялись.
