# Локальный пилот 64 пользователей — генератор признаков

Статус: реализация API для пилота; тестируется на синтетических примерах. Признаки в реальных Yambda данных ещё не рассчитаны и их качество не оценивалось. Файлы данных и историю читает/выбирает вызывающий код.

## API и контракт причинности

Импорт: `from task_01_auto_features.src.pilot_features import FeatureEngine`.

Создание: `FeatureEngine(artist_map: dict[int, tuple[int, ...]], album_map: dict[int, tuple[int, ...]], short_window: int, half_life: int)`. Оба временных параметра заданы в **исходных целочисленных единицах timestamp**; модуль не конвертирует их в секунды/дни и не трактует timestamp как Unix-время. `half_life` задаёт half-life затухания в тех же единицах.

`observe(event: dict)` принимает `uid`, `item_id`, `timestamp`, `event_type` в неубывающем порядке timestamp. Разрешённые типы — `listen`, `like`, `dislike`, `unlike`, `undislike`. `unlike` и `undislike` добавляют событие активности и обновляют давность, но не считаются дополнительным like/dislike-счётом. Каждый вызов добавляет ровно одно наблюдение; вызывающий код отвечает за то, чтобы до запроса t передавались только события с timestamp < t. `transform` проверяет, что максимальный уже наблюдённый timestamp строго меньше query timestamp; передача целевого события или любого события той же метки времени приведёт к ошибке, а не к утечке.

`transform(user_id: int, item_ids: list[int], timestamp: int)` возвращает numpy.float32 матрицу формы `(len(item_ids), len(feature_names))`. Запрос не меняет историю. Несколько запросов в один момент времени допустимы; до них нельзя добавлять события с timestamp, равным этому моменту. Объекты, пользователи и пары не перечисляются плотными матрицами: внутренние накопители разреженно создаются только при наблюдении соответствующего события. Временные ряды используют компактные массивы timestamp и префиксных сумм, а не копии полных словарей событий.

Маппинги рассматриваются как фиксированный снимок, одинаково доступный на каждом query. Их временная доступность не проверяется этим классом и остаётся явно принятым пилотным допущением. Повторяющиеся entity ID в mapping нормализуются через `set`; идентификаторы не выводятся как числовые модельные признаки. `played_ratio_pct`, `track_length_seconds` и `is_organic` намеренно не используются: доступность завершённого сигнала и его связь с точкой запроса не установлена.

## Признаки и стабильный порядок

`feature_names` — список строк в порядке колонок; `feature_groups` — словарь `{feature_name: group}`. Группы сериализованы как U, затем I, D, C, X. Имена и порядок не зависят от содержимого входных mapping.

| Группа | Состав |
| --- | --- |
| U | `events`, `listen`, `like`, `dislike` counts за всю наблюдённую историю и за short window; последняя давность события и `known`. События unlike/undislike входят в `events`, но не отдельные типовые счётчики. Все U признаки одинаковы для кандидатов одного пользователя и времени. |
| I | Те же counts/окна, recency и known по item; i_artist_degree и i_album_degree — численность уникальных связей объекта в фиксированном mapping. |
| D | Counts активности и listen/like/dislike по точной паре user-item за полную и короткую историю; recency и known. |
| C | Для artist и album кандидата: causal user-entity counts активности/listen/like/dislike за полную и короткую историю, агрегированные по уникальным категориям кандидата через `max`, `mean` и долю категорий, на которые есть любая история (`knownshare`). Пустой набор категорий даёт нули. |
| X | Half-life затухшие counts для I и D по activity/listen/like/dislike; для user-artist и user-album — те же сигналы с `max` и `mean` по категориям кандидата, плюс один `knownshare` на relation (доля категорий с любой историей события). Эта группа содержит только признаки непрерывного затухания. |

Short window определено как открытое слева `(query_timestamp - short_window, query_timestamp)`. Например, timestamp ровно `query_timestamp - short_window` исключается. Для отсутствующей истории counts и X равны 0; recency равна -1; known и knownshare равны 0; все результаты конечны. Степени artist/album отражают число уникальных связей из фиксированного mapping и доступны даже у пустой истории.

Каждое исходное событие добавляет ровно 1 к activity-сигналу пользователя, объекта и прямой пары. Для C исходный вклад распределяется как `1/k` между k уникальными artist (и отдельно между k уникальными album). Так один event не удваивается из-за many-to-many связи, а профиль конкретного user-entity остаётся взвешенной историей. Степени artist/album в I являются только item attributes. Fractional contribution `1/k` применяется здесь отдельно к профилю C по ключу `(user, entity)`.

Half-life сигнал для истории событий `e` с весами `w_e`: `sum(w_e * 2 ** (-(query_timestamp - event_timestamp) / half_life))`. Для U-I-D вес равен 1; в C вес равен `1/k`. В реализации состояния затухания обновляются при `observe`, а `transform` только применяет коэффициент от последнего наблюдённого времени к query timestamp и не мутирует причинную историю.

## Тесты

`tests/test_pilot_features.py` покрывает неизменность префиксных признаков при изменении не переданных будущих событий; исключение target на уровне orchestration-контракта; удаление duplicate mapping ID и fractional credit; повторные запросы одного timestamp без изменения состояния; пустую историю и конечные defaults; аналитическую half-life точку; границу короткого окна; постоянство имён и меток групп. Это синтетические unit tests, не аудит полной таблицы и не результат качества модели.
