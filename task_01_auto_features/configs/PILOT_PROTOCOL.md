# Протокол пилота pilot_001

Зафиксирован до обучения 25 октября 2026 года. Цель пилота — проверить сквозной процесс, вклад групп и стоимость; это development-эксперимент, не итоговый test исследования. Конкретные параметры: [pilot_001.json](pilot_001.json).

## Данные и время

Случайно выбрать 64 uid с одинаковой вероятностью из опубликованного Yambda-50M, seed 20261025. Сохранить все их события по всему опубликованному горизонту; случайно выбирать отдельные строки истории нельзя. Совокупность пользователей определяется как офлайн-когорта по имеющемуся файлу, без отбора по будущей активности. Полнота относительно 5B не доказана.

Справочники artist/album использовать как фиксированный снимок метаданных с явным допущением доступности этих связей для известных объектов. Дубли связей удалять. Каталог для запроса — объекты, уже наблюдавшиеся строго до t у выбранных пользователей; глобальные популярности также по выбранной когорте.

Время — исходный монотонный timestamp, без объявления его Unix-временем или пересчёта в календарные дни. Глобальные границы на квантилях timestamp выбранных событий: p30 — начало обучающих запросов, p70 — train_end, p85 — validation_end. Train: p30 <= t < p70, validation: p70 <= t < p85; t >= p85 полностью резервируется. Равные метки не разрываются.

Допущение офлайн-replay: запись события становится доступна на его logged timestamp. Перед запросом доступны только события с timestamp < t. События с равными метками не видят друг друга. Итоговую долю прослушивания и длительность не использовать в признаках пилота, поскольку время доступности результата не подтверждено. Текущий `is_organic` целевого события не использовать.

## Запросы, цель и кандидаты

Цель — один следующий зарегистрированный `listen` на выбранном моменте запроса. Запросы строятся на временных метках listen; в пределах одного uid/timestamp с несколькими listens такой неоднозначный запрос исключать и считать отдельно. Из подходящих запросов равномерно воспроизводимо выбрать максимум 30 train и 10 validation на пользователя. История при этом не сокращается.

Фиксированный генератор использует только прошлое: популярные объекты, недавно прослушанные пользователем треки, объекты предпочитаемых исполнителей и альбомов. Общий лимит 100, квоты 25/25/35/15, недобор заполняется популярными. Порядок и ничьи детерминированы; кандидаты уникальны. Target никогда не добавляется после просмотра метки.

Обучаем классификатор на запросах, где target попал в кандидаты: один наблюдаемый положительный объект против остальных неотмеченных кандидатов. Это условная обучающая выборка; вероятность события и естественная калибровка из неё не выводятся. Пропуски target в validation сохраняются и дают нулевые end-to-end метрики. Сообщать долю запросов, не вошедших в обучение из-за retrieval.

Срезы repeat/new и warm/cold определяются исключительно по истории до t. До ограничений по известности каталога сохраняется исходный target и полный знаменатель.

## Признаки и сравнения

U: активность/типы прошлых событий/давность. I: прошлые популярности, давность и степени mapping. D: прошлые действия конкретной пары. C: пользовательские профили artist/album с нормированным вкладом 1/k по уникальным связям. Все четыре группы числовые и причинные; raw ID в модель не передаются.

Короткие окна задаются в raw timestamp units как доли (p70 - min timestamp), без названий календарных дней. Ручной вариант — 1/30 этого диапазона; ограниченный автоматический поиск проверяет ещё 1/100 и 1/10. Положительные длины округляются вниз с минимумом 1. Half-life для отдельной гипотезы — 1/30 development-диапазона; это дополнительная группа X.

Сравнить popularity; I; U+I; U+I+D; U+I+C; U+I+D+C; I+D+C; U+D+C. Повторяющиеся leave-one-group-out наборы не обучать второй раз. Фиксированные 120 итераций CatBoost depth=5, 2 CPU-потока и один seed для всех вариантов. Затем X и две альтернативы окна при той же модели. Масштаб поиска ограничен тремя окнами, результат относится к этой сетке.

Выбор лучшего набора/окна — только по validation NDCG@20. Это первичная проверка работоспособности, не подтверждение устойчивости/значимости улучшения. Финальный test не раскрывать и не оценивать. Позднейшая широкая разработка может использовать те же development-данные; итоговый test остаётся зарезервирован.

## Метрики и стоимость

Recall@10/20, NDCG@10/20, candidate recall. Сначала усреднение по запросам внутри пользователя, затем по пользователям; отдельно query-micro при необходимости. Для одной цели DCG = 1/log2(rank+1), ideal DCG=1. Пропуск кандидатов и cold target не удаляются из знаменателя. Ничьи: score DESC, item_id ASC. Отчёт содержит число запросов/пользователей и срезы repeat/new.

Сохранить конфигурацию и её хеш, хеши кода, модели, предсказания, таблицы метрик, размеры данных, feature count, время подготовки/обучения/оценки и пик RSS. RSS сэмплируется фоновым монитором и на Windows дополняется peak_wset, когда доступен. Один тяжёлый процесс за раз; не строить плотную матрицу всего каталога. При достижении лимита остановиться с сохранённым статусом и уменьшить число запросов/кандидатов, сохраняя историю.

## Условия принятия

Проверки на малых искусственных данных должны обнаруживать утечки будущего, ошибки на границе batch, дубли mapping, неверные ничьи и удаление пропущенной цели из знаменателя. Независимый субагент проверяет runner до интерпретации результатов. Успешный пилот означает рабочую воспроизводимую процедуру и измеренные затраты; размер выборки, один seed, snapshot mapping, условная train-выборка и development-оценка ограничивают выводы.
